The Problem
01 · The problem

The work was in the platform.
The conversation was not.

Six teams managing one deal over months. Each team communicating in different tools, with different people, leaving different records. Every handoff a context gap.

BO → PM: NDA summary forwarded. Legal not included.
Legal → BD only: territory concern. PM unaware for 3 days.

Ticket raised. Copy-pasted email context. 3 people missing.

02
Architecture
02 · How we thought about it

Not a messaging tool.
A communication layer.

We mapped four architectural layers before sketching a screen. Each layer has a hard boundary. Information flows outward only by deliberate action.

01
Internal Thread
Foundation layer
Anchored to customer and lifecycle stage. Started from inside the workflow, not a messaging surface. Scoped to relevant roles.
02
Tagged Messages
Signal layer
Five intent types chosen before sending: Update, Concern, Decision Request, Approving, Escalating. Each tag is a filter axis across every thread.
03
External Messages
Default view
Messages marked for customer visibility. These become selectable as context when starting a Customer Thread. External is the default view on thread entry.
04
Customer Thread
Hard boundary
Created from inside an internal thread only. One per thread, enforced architecturally. External messages become selectable context. Customers cannot initiate.
Customers cannot access Layers 01–03 · architectural boundary, not a permission toggle
Where threads start
Communications button on every workflow page.
LT reviewing a contract, BO on a customer page – both see it top-right. New Thread or Raise Ticket. Customer and stage pre-filled.
Where you return
My Threads – the monitoring surface.
All active threads across all customers. Quick-filter chips, full table. Threads are initiated in context. My Threads is where you check, triage, and continue.
Design Principles

Three rules that
governed every decision.

01
Context before conversation
A thread without a customer is a chat. Anchoring to customer + stage before the first message was non-negotiable.
02
Intent before sending
Forcing a tag at compose time — Update, Concern, Decision — turns noise into signal. You can't filter on what you never captured.
03
Boundaries enforced, not asked
One customer thread per internal thread. Customers can't initiate. These are architecture — not defaults that erode under pressure.

04
Hard Constraints
04 · Hard constraints

Enforced. Not advised.

The customer thread model has architectural boundaries. Not guidelines that erode under pressure.

✓
Started from inside an internal thread only
Never from a standalone surface. The internal thread is the prerequisite. Customer and stage are always known.
✓
External messages as selectable, editable context
The team curates what the customer sees. All editable before the thread starts.
×
Cannot start a second customer thread from the same internal thread
One per thread. Enforced architecturally. Multiple threads splits the record and creates lineage ambiguity.
×
Customers cannot initiate
Customers can only be added to a thread that already exists. Architectural boundary, not a permission setting.
05
Learnings
05 · Learnings

Three things
that didn't leave.

1
The hardest problem was the model of initiation. Where a conversation starts shapes everything it can become.
2
External as the default view was the most contested call. It turned out to be the most important one.
3
This was not messaging. It was binding — tying every conversation to customer, stage, intent, and outcome so none of it could exist in isolation.
